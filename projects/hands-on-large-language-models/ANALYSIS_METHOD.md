# 我们应该怎样分析这个仓库

目标不是逐个运行 Notebook 后写“成功”，而是建立一条从源码证据到真实能力验证的研究链路。

## 总原则

每项能力都需要回答六个问题：

1. **它声称能做什么？** README、章节名称和 Markdown 如何描述能力？
2. **代码实际上做了什么？** 使用了哪个模型、数据集、库、输入和输出？
3. **依赖什么条件？** CPU/GPU、显存、API Key、网络、许可证和版本分别是什么？
4. **结果如何衡量？** 有没有基线、指标、对照组和可重复的随机种子？
5. **离生产还有多远？** 是否缺少服务化、测试、监控、安全、成本和故障恢复？
6. **怎样形成我们的增量？** 中文化、现代化、评测、工程化或新的可视化是什么？

## 第一层：静态结构分析

检查对象：

- 根目录和章节组织；
- 许可证、提交哈希和维护状态；
- Python、CUDA和依赖版本；
- Notebook 数量、代码单元和 Markdown 单元；
- 模型、数据集、API、训练器和向量数据库引用；
- 是否存在包结构、测试、服务入口与部署配置。

产物：`analysis/notebook-inventory.json` 和本项目 README 中的能力地图。

通过标准：每项公开能力都能定位到具体 Notebook 和代码对象，不能只引用上游 README。

## 第二层：单章最小复现

每一章都建立相同的实验记录：

| 字段 | 要求 |
| --- | --- |
| 上游版本 | 固定 commit |
| 环境 | Python、操作系统、CPU/GPU、显存 |
| 输入 | 固定的小样本或数据集切片 |
| 模型 | 完整模型 ID、revision、量化方式 |
| 操作 | 从空环境开始的可复制命令 |
| 输出 | 日志、结果文件、截图或指标 |
| 成本 | 下载量、运行时间、显存、API费用 |
| 结论 | 已验证、未验证和失败原因分开记录 |

建议先运行第 1—3 章，确认基础模型、Tokenizer 和生成流程，再进入应用章节。

通过标准：另一台机器依据记录可以得到结构相同的结果；仅保留 Notebook 已有输出不算复现。

## 第三层：能力评测

不同能力采用不同指标：

| 能力 | 建议指标 |
| --- | --- |
| 分类 | Accuracy、Macro F1、混淆矩阵、延迟 |
| 聚类/主题 | Topic coherence、离群率、人工一致性 |
| 语义检索 | Recall@K、MRR、nDCG、检索延迟 |
| RAG | 检索命中率、回答忠实度、引用正确率、成本 |
| 多模态 | Recall@K、描述质量、视觉问答准确率 |
| Embedding | MTEB 子集、领域检索指标、推理吞吐 |
| 微调 | 任务指标、训练成本、灾难性遗忘、基线差值 |

所有实验必须保留未修改的基础模型作为对照，避免只展示一个看起来合理的输出。

## 第四层：跨章节整合

选择一个真实的小型项目，把多章能力串起来。首选方向是中文知识库问答：

```text
文档解析
→ 分块
→ Embedding
→ FAISS/其他向量库
→ 检索与重排
→ 本地或云端生成模型
→ 引用答案
→ 自动评测
```

整合阶段要补齐原仓库未覆盖的内容：配置、模块边界、测试、API、前端、日志、缓存、权限和部署。

## 第五层：形成我们的研究增量

研究成果不应是上游 Notebook 的镜像，而应至少包含一项新增价值：

- 中文数据与中文模型复现；
- 原版依赖与当前依赖的兼容性对比；
- 统一评测数据和指标；
- CPU、消费级 GPU 与云端 GPU 成本对比；
- Notebook 到模块化服务的工程改造；
- 可公开访问的交互演示；
- 失败案例、局限和适用边界。

## 建议研究顺序

```text
基础机制：01 → 02 → 03
常用应用：04 → 05 → 08
交互方式：06 → 07
跨模态：09
模型训练：10 → 11 → 12
```

这个顺序优先建立对 Token、Embedding、生成和检索的理解，再进入高成本的模型训练，能减少“代码跑通但不知道为什么”的情况。
