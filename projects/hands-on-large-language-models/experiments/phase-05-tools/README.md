# 第7章实践：工具到底是谁执行的？

本实践不复述“Agent会调用工具”的概念，而是把Notebook中的ReAct链拆成可检查的责任边界：模型产生或接收文本，控制器决定怎样组织步骤，Python函数实际计算，最后模型再把工具观察写成回答。

## 先读代码得到的真实结构

固定上游提交：`ea3390819997999a51983677b80b3aac4dc50ada`。

| Notebook代码 | 实际作用 | 不能误解成 |
| --- | --- | --- |
| 8—17 | PromptTemplate与多个LLMChain顺序传值 | 模型内部新增了工作流能力 |
| 22—25 | ConversationBufferMemory把全部历史放回提示词 | 模型参数永久记住用户 |
| 27—30 | WindowMemory只保留最近2轮；旧年龄随后被挤出 | “记忆”是无限可靠数据库 |
| 32—36 | 同一模型把历史改写成摘要 | 摘要等于原始记录 |
| 39—42 | ReAct格式、工具注册、AgentExecutor执行循环 | 模型自己访问了搜索引擎或计算器 |

Notebook还存在需要先说明的完整性问题：

- cell 6保存了空的原始`llm.invoke`输出，而带Phi-3模板的cell 10对同一问题正常回答，说明提示封装会改变表现。
- 全章继续使用已弃用的`LLMChain`，cell 12保存了弃用警告。
- WindowMemory的`k=2`只保留最近两轮；询问姓名后，最早给出的年龄已经不在下一轮提示词中。
- SummaryMemory由生成模型改写历史，保存摘要加入了原对话没有的隐私解释和性别代词。
- Agent示例需要占位OpenAI密钥、实时DuckDuckGo和含糊的“当前MacBook Pro价格”，不能作为稳定离线基准。

## 本轮问题

> 同一模型、同一换汇任务和同一回答要求下，把Python计算器的正确结果作为工具观察交给模型，最终答案会怎样变化？

这里特意不使用网络搜索。12个正式任务都直接给出USD金额和汇率，Python使用`decimal.Decimal`计算并四舍五入到两位小数。

## 控制变量

固定项：

- 模型：`HuggingFaceTB/SmolLM2-135M-Instruct`
- 模型修订：`12fd25f77366fa6b3b4b768ec3050bf629380bac`
- 12个正式任务、原生chat template、greedy解码、seed 42、最多32个新token
- 回答契约：回答末尾数字必须是两位小数的EUR金额

唯一变化：

- `model-only`：不提供工具结果，让模型自己乘法。
- `python-calculator-observation`：Python先精确计算，再把结果作为一行观察交给同一模型。

初始JSON式回答契约会诱导135M模型写Python代码或重复示例。正式先导实验前，先用独立提示探针把两组共同契约收缩为“最后一个数字”，避免把代码生成倾向当成工具效果。探针不参与四条先导和十二条正式任务的评分。

## 正式结果

| 变体 | 有末尾数字 | 回答中出现正确工具值 | 最终金额正确 |
| --- | ---: | ---: | ---: |
| 模型单独计算 | 10 / 12 | 0 / 12 | 0 / 12 |
| 提供Python工具观察 | 12 / 12 | 7 / 12 | 4 / 12 |

先导集是0/4 → 2/4，因而正式运行前预测工具观察会提高最终金额正确率；正式集0/12 → 4/12，方向得到确认。

## 失败告诉了什么

工具路径并不是一次成功：

1. Python执行器12/12都得到了正确`Decimal`结果。
2. 小模型只在7/12回答中复述了这个正确值。
3. 只有4/12把它保持为回答最后一个数字。
4. 另外3条虽然说过正确值，随后又追加汇率或错误数字，因此严格判错。
5. 其余5条忽略观察、重新计算、套用无关公式或在32 token处截断。

因此“Agent答错”可能来自工具选择、动作解析、工具执行、观察传递或最终生成。只看最终答案无法知道哪一层坏了。

## 你应该形成的理解

- **模型**：根据当前提示生成Action或Final Answer文本。
- **Memory**：外部代码选择并重新放入提示词的历史，不是模型权重自动更新。
- **Tool**：真正执行搜索、计算或数据库操作的函数/API。
- **Executor**：解析动作、调用工具、把Observation交还模型的控制循环。
- **Chain**：把上一步输出映射为下一步输入，不保证每一步内容正确。

## 继续修改

在看结果前先写预测，然后只改一项：

1. 把`max_new_tokens`从32改为64：截断会减少，但模型追加错误数字是否增加？
2. 在观察后加入显式`FINAL=`分隔符：正确工具值能否更稳定地成为最后一个数字？
3. 故意提供一个错误工具观察：模型会盲目服从还是重新计算？
4. 增加独立的Action生成与解析阶段：分别统计工具选择、参数复制和最终回答正确率。

理解检查：为什么本轮Python计算器可以12/12正确，而完整工具路径仍只有4/12？如果只保存最终答案，你会丢掉哪些诊断信息？

## 证据边界

- 使用135M缓存代理模型，不是Notebook里的Phi-3 llama.cpp和OpenAI模型。
- 实验只隔离“是否提供工具观察”，没有评测模型能否自主选择工具或输出可解析ReAct动作。
- 12条数据是合成换汇任务，汇率由任务给定，不包含实时价格或市场数据。
- 工具观察提升了本轮正确率，但4/12仍然很低，不能推出“接上工具就可靠”。
- greedy解码便于复现，不覆盖采样方差。
