## 1. 阶段结论

这个项目对我们的意义成立，但意义不在于“得到一套可直接改成任意 3D 产品的完整框架”，而在于获得了一份可运行、可拆解的 Three.js 程序化 3D 参考。

Phase 01 已回答四个核心问题：

1. **它能实现什么效果**：可交互载具、程序化场景、地形、材质、粒子、光照、镜头、HUD 和反馈系统可以共同组成完整的网页 3D 表达。
2. **为什么视觉效果成立**：并非依赖单个高精模型，而是依赖统一风格、轮廓比例、材质分层、灯光阴影、环境密度、动效反馈与镜头构图的协同。
3. **哪些能力可以复用**：渲染底座、相机、输入、实体组织、程序化造型、材质主题、特效和性能策略可以提炼；坦克与沙漠内容本身不能被误认为通用产品组件。
4. **风险和边界是什么**：程序化低多边形路线适合快速原型和风格化表达，但不等同于高保真产品模型、工业 CAD、数字孪生数据链或无限规模场景。

因此本阶段停止继续堆叠场景和功能，保留研究链、演示入口、证据与恢复条件。

## 2. 研究对象与来源边界

### 上游原始能力

上游仓库提供游戏本体及其主要 3D 表现。核心视觉资产以 Three.js 几何体、材质、灯光、粒子和运行时代码组合为主，重点内容是载具、地图、交互和战斗反馈。

### 我们增加的研究层

本地研究没有宣称新增一套通用 3D 引擎，而是围绕上游能力增加：

- 研究控制台与页面导航；
- 产品展台，用于隔离观察单一实体与材质；
- 视觉层实验室，用于拆分几何、材质、灯光、环境与后期层；
- 沙漠能力场景，用于观察组合后的系统表现；
- 能力、证据、预算、风险和扩展方向登记；
- 阶段归档页与可复核的浏览器报告。

必须始终区分：**展台是产品观察逻辑，沙漠是环境/游戏场景逻辑，两者是同一渲染技术的不同验证面，不是同一个业务场景。**

## 4. 已验证的能力

### 4.1 程序化实体

- 使用基础几何体组合载具和场景物件；
- 通过父子层级组织炮塔、履带、轮组和附件；
- 通过比例、轮廓和局部细节建立可辨识度；
- 在没有外部高精 3D 模型的情况下形成统一的低多边形风格。

### 4.2 地形与环境

- 程序化地形、地表色彩与空间边界；
- 植被、石块、建筑等重复物件的场景填充；
- 雾、天空、环境色与远近层次；
- 沙漠地图是组合验证，不是通用展台的背景模板。

### 4.3 材质、灯光与阴影

- 基于 PBR 参数的材质差异；
- 主光、环境光、阴影和色调映射形成体积感；
- 同一几何可通过材质主题表现不同产品语义；
- 光照、背景和材质必须成套校准，单独替换颜色不能保证观感。

### 4.4 镜头与交互

- 展台式环绕观察；
- 游戏式跟随/驾驶视角；
- 热点、HUD 和输入反馈；
- 镜头构图承担了很大一部分“看起来不错”的效果。

### 4.5 动效与反馈

- 载具运动与部件联动；
- 粒子、烟尘、炮火和命中反馈；
- 动画、声音、屏幕反馈可以形成统一的操作手感；
- 这些效果属于运行时系统，不是静态模型自带品质。

### 4.6 数据与页面组织

- 同一能力可分别进入展台、实验室、组合场景和说明页面；
- 研究注册表统一登记演示、证据、性能预算和风险；
- 页面外壳不加载 Three.js，可作为低成本控制面。

### 4.7 性能意识

- 页面按研究用途拆分，避免每个入口都启动完整场景；
- 通过请求数量、加载时间、移动端路线和视觉检查保存性能证据；
- 当前结果证明“可运行”，不代表已经完成生产级优化。

## 5. 为什么它看起来不错

它的观感主要来自系统配合，而不是 Claude 或 Three.js 自动生成了“好看”按钮：

1. **明确的风格约束**：低多边形、统一色盘和适度简化减少了不一致。
2. **可读轮廓**：载具比例、炮塔、履带和附件让对象在远处仍可辨识。
3. **密度分层**：大地形、中尺度建筑/植被、小尺度石块/粒子共同避免空洞。
4. **光照与空气透视**：阴影、雾和背景层次建立空间深度。
5. **镜头选择**：视角、距离和运动速度控制了用户看到的画面质量。
6. **动态反馈**：移动、烟尘、开火和界面反馈让简单几何获得生命感。
7. **代码迭代**：Claude 可以帮助生成、修改和组合代码，但最终效果仍来自明确审美约束、反复观察和参数校准。

## 6. 可复用判断

| 层级 | 可复用性 | 说明 |
| --- | --- | --- |
| Three.js 渲染初始化 | 高 | 场景、相机、渲染器、循环和尺寸适配可抽取为底座 |
| 相机与输入系统 | 高 | 可支持展台、漫游、跟随等不同控制模式 |
| 实体层级与生命周期 | 中高 | 需要从坦克语义改成数据驱动实体接口 |
| 材质主题与灯光方案 | 中高 | 可形成风格预设，但需针对新内容重新校准 |
| 粒子与反馈系统 | 中 | 逻辑可复用，表现和预算需按场景调整 |
| 程序化载具构造 | 中 | 技术路线可复用，具体坦克几何不等于通用产品模型 |
| 沙漠地图内容 | 低 | 可作为环境生成案例，不应成为其他业务的默认基座 |
| 游戏规则与战斗逻辑 | 低到中 | 仅在类似互动/教学/模拟需求中有价值 |

结论：**可以把它当作 Three.js 能力研究基座和程序化风格参考；若要制作其他 3D，应复用系统模式，而不是直接复制沙漠与坦克内容。**

## 7. 已有证据与性能事实

本阶段保留以下事实，不把它们包装成生产指标：

- 产品工作台桌面 Atlas 路线记录 116 个请求；
- 产品工作台 Nova 路线记录 51 个请求，移动路线 37 个请求；
- 工作台 30 项检查与 8 项预算通过；
- 视觉层实验室 20/20 功能检查通过，但一次完整验证耗时约 55.038 秒，高于 30 秒研究目标；
- 沙漠能力场景完整验证约 22.861 秒，并观察到 17 类效果；
- 完整移动战斗路线约 73.9 秒，高于 45 秒目标；
- 研究控制台无 Three.js 运行时，首轮记录约 142ms 就绪；
- 阶段归档页不加载 Three.js、模型、图片或视频；桌面、移动、键盘和 reduced-motion 检查均已建立。

这些数字的意义是标记负载分布和风险。它们不能跨设备直接比较，也不能替代目标设备上的 FPS、GPU frame time、显存和内存分析。

## 8. 风险清单

1. **语义错位**：把坦克/沙漠直接改名为工业展示，会导致视觉内容和说明不一致。
2. **程序化造型上限**：适合风格化和概念演示，不适合精确复刻复杂商品或工业设备。
3. **场景规模**：大量独立网格、阴影、透明粒子和后处理可能快速增加 draw calls 与 GPU 成本。
4. **移动端差异**：桌面可运行不代表中低端移动设备稳定。
5. **研究页面膨胀**：继续增加入口而不收敛结论，会让演示变成杂乱页面集合。
6. **来源归属**：必须区分上游原始实现与本地研究扩展，避免把本地说明误认为上游功能。
7. **Claude 归因**：仓库名称和开发方式可能与 Claude 辅助有关，但画面来自代码、参数和迭代结果，不能据此推断为模型自动生成的完整 3D 资产。

## 9. 暂停项与恢复条件

本阶段不继续实现以下内容：

- GLB/GLTF 高精资产管线；
- CAD/BIM/实时数据驱动的数字孪生；
- 全新工业展厅、虚拟展厅或军事剧情；
- 自动镜头编排和宣传视频导出；
- 大地图流式加载、多人同步或完整编辑器；
- 面向上线产品的全面性能改造。

只有出现明确需求时才恢复：

| 研究方向 | 恢复触发条件 |
| --- | --- |
| 外部 3D 资产管线 | 获得明确的 GLB/GLTF 产品资产和验收画面 |
| 数字孪生 | 有真实设备结构、实时数据源和业务操作流程 |
| 虚拟展厅 | 有空间脚本、展品清单、品牌视觉和目标终端 |
| 教学模拟 | 有教学目标、操作步骤、错误反馈与评估标准 |
| 自动宣传视频 | 有镜头脚本、输出规格和离线渲染质量目标 |
| 性能专项 | 有目标设备、场景规模、FPS 与加载预算 |

## 10. 如何恢复本研究

下一次继续前，先做四件事：

1. 阅读本文件和 `/research/archive`，确认新需求是否命中恢复条件；
2. 从 `/workbench` 选择一个最接近的可复用系统，不要直接从沙漠场景复制内容；
3. 为新实验写清资产来源、画面目标、交互范围、目标设备和性能预算；
4. 新建独立路线和证据目录，不改写 Phase 01 的历史报告。

本地启动与复核命令以项目 README 和归档包说明为准。Phase 01 的报告、截图和校验清单位于 `evidence/` 与 `archive/threejs-capability-research-phase-01-2026-08-26/`。
