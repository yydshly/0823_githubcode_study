# Goal-driven model policy

本项目的目标不是展示已经接入了多少模型，而是把用户的想法转化为优秀、可信、可运行的 Three.js 网页。

## 决策顺序

每次生成或扩展都按以下顺序判断：

1. 用户想让访客理解、记住或完成什么。
2. 页面需要形成什么核心视觉记忆与使用体感。
3. DOM、WebGL、真实素材和交互分别承担什么职责。
4. 当前运行时能否诚实实现。
5. 哪项模型能力能产生可验证的增益。
6. 增益不足时不调用；能力不足时保留缺口或要求真实输入。

页面章节数量、镜头结构和视觉路线由目标决定，不由固定模板或本文档决定。

## Provider 角色

- Codex：优先承担整体创意、ExperienceBlueprint、镜头与页面编排。它不是默认素材生成器。
- MiMo：可替代承担结构化创意与页面蓝图；只有显式选择或 Codex 不可用时才参与。
- MiniMax 文本模型：可承担创意解释，但不会仅因配置成功而进入一次运行。
- MiniMax 图片模型：只处理通过 AssetUsePolicy 的建议性图片、纹理或精灵需求。
- Local：用于离线基线、回退和诊断，不冒充模型创意质量。

`auto` 只选择一个创意 provider。它不会同时调用多个文本模型来制造表面上的“组合能力”。

## 素材使用门禁

图片生成必须同时满足：

- EffectSpec 显式声明素材需求；
- 至少一个可见效果层引用该需求；
- `visibleOutcome` 能说明素材将改变什么；
- 素材不承担准确事实、真实产品、品牌、UI、文字或信息证据；
- 预期收益足以改善主体、空间层次或最终记忆点；
- 首屏负载预算允许；
- 单次最多批准两个最高收益需求。

以下情况禁止调用生成器：

- `accurate` 产品、品牌、UI、文字和信息证据；
- 没有被效果层引用的孤立需求；
- 可选的纯装饰氛围；
- 只是为了使用已配置 provider；
- 生成结果会让用户误以为它是真实产品或正式证据。

生成素材初始只视为 `L2-inspectable`。它必须继续通过视觉、许可、负载和浏览器审核，不能自动升级为可发布素材。

## Three.js 使用约束

DOM 承担可读内容、操作、语义和回退；WebGL 承担空间记忆、氛围、镜头和互动关系。

Three.js 效果必须至少改善一项：

- 建立主体或空间坐标；
- 解释关系、结构或能力；
- 形成区别于普通网页的记忆点；
- 让用户操作获得有意义的视觉反馈。

如果 WebGL 只是背景装饰、持续旋转或无目的粒子，应简化为更低成本的实现。

## 验收证据

一次能力接入只有在以下证据链成立后才算有效：

```text
目标与输入
  -> EffectSpec / ExperienceBlueprint
  -> 本地 Schema 与使用门禁
  -> 真实浏览器页面
  -> 视觉与交互评审
  -> 有边界的结论
```

构建通过、截图存在或 API 返回成功，只能证明链路运行；不能单独证明最终效果优秀。
