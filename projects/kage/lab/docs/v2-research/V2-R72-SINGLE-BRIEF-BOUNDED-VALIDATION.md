# V2 R72 · 单 brief 有界端到端验证

## 目标

不用旧主题、不扩展能力目录、不生成多个候选，验证当前系统是否能够在固定时间内把一个新想法送到明确终态，并在质量不足时正确停止。

## 输入

主题为“社区合唱团和声排练台”：用户调整四个声部比例和排练问题时，乐谱、波形、歌词与建议应同步变化；页面应是明亮、横向、持续存在的工作台，不使用暗色电影长滚动或中央 3D 产品。

任务：`job-ce11224caa40aa54`

唯一结果：`dedicated-afdb8c23b1a5`

## 运行事实

- 规划选择 `dom-only / procedural / static-sufficient`，没有等待图片素材。
- Codex 5.6-sol 只执行一次 authoring，没有第二候选。
- 原任务约 186 秒到达 `review-required`，低于五分钟总截止时间。
- 页面没有浏览器错误、资源错误或横向页面溢出；桌面和 390px 页面均可运行。
- 结果没有归档到案例库，也没有自动循环修复。

## 验收器缺陷与修正

首次结构预检同时记录了：

- `semanticState.inputChanged = true`
- `semanticState.outputChanged = true`
- `semanticState.parameterActionObserved = true`
- `interactionInputObserved = false`

旧逻辑只看最后一个通用标志，因此误判“交互未观察”。R73 将显式参数动作和高层动作都视为直接交互证据；新增回归测试后，机械复验从 86 提升为 100。

## 独立视觉结论

机械通过不代表最终质量通过。一次独立视觉验收得到 70 分并要求修改：

- 声部比例变化没有形成足够明显、可归因的乐谱色块和点阵变化。
- “节奏不齐”主要改变数值与说明，核心和声主体变化偏弱。
- 390px 手机端只能看到被裁切的横向乐谱，配置、解释和最终行动未形成完整路径。
- 工作台与结尾之间空白偏大，节奏松散。
- 首屏更像通用数据网格，产品闭环仍依赖较多文字解释。

最终状态保持 `review-required / rejected / 70`，不进入案例库。

## 对第一目标的意义

这次验证证明了两件事：

1. 有界管线已经能够在质量不足时于一次候选后停止，不再无限重做。
2. 下一项系统缺口不是增加更多模型或特效，而是把“主要交互必须产生显著主体差异”和“移动端必须拥有完整等价任务路径”前置到 Codex 执行合同和快速预检。

后续只应修改这两个合同/门禁，再使用新的 brief 验证；不应继续人工精修本候选来制造通过结果。
