# V2 R26：生成质量与耗时护栏

## 本轮设计契约

- 入口模式：revision-led + repair-led。
- 已获授权：用户确认直接执行，不需要再次确认方案。
- 第一目标：用户描述一个想法后，系统以研究沉淀为约束，选择合适的页面体验架构，生成一个可运行、可解释、视觉可信的网页。
- 本轮不新增案例、不扩展业务、不接入新模型；只修生成链路中的质量判断、架构选择和耗时边界。
- 保留：现有工作台、Codex 单候选生成、素材合同、Three.js/Canvas/DOM 混合运行时、精选案例归档。

## 已观察证据

最新“街坊风扇诊断台”首次生成虽然编译通过、机械评审 100 分，但 SDK Canvas 被位于其上方的不透明语义根节点完全遮挡，真实浏览器里主体不可见。人工修复后才能成为合格案例。另一次自动视觉精修等待 90 秒后超时。

根因不是 Three.js 不会渲染，而是当前质量门只检查“Canvas 是否存在”，没有检查“Canvas 是否被上层整屏内容遮挡”；同时未知 brief 默认进入连续长滚动，自动精修最多两轮，使模型获得了不必要的探索空间。

## 本轮三个可验收结果

1. 可见性门禁：在 opening、final、mobile 等实际浏览器帧中，识别 SDK Canvas 上方覆盖大部分视口的不透明直接兄弟层；命中时机械评审必须阻断，不能归档。
2. 有限架构选择：只有 brief 明确表达滚动、逐渐形成、穿越或时间推进时才选择 continuous-scroll；未知主题回落到较低成本的 editorial-field，而不是默认电影式长滚动。
3. 有界精修：一个主候选最多执行一次基于证据的模型精修；机械门禁与独立视觉验收仍未通过时进入 review-required，不再开放第二轮探索。

## 验收结果

- 机械门禁新增 `canvas-occluded` blocker。浏览器采集会检查 `.generated-canvas` 上方近乎整屏（≥94% 视口）的不透明直接兄弟层及其后代；阈值经过真实末段预约面板回归校准，避免把正常 82% 内容区误判为整屏遮挡。
- `dedicated-5694e0a3a022` 真实浏览器回归：opening、beat-middle、final、mobile 均 ready，Canvas=1，occluded=false，horizontal overflow=0。
- 未指定动态结构的普通网页回落 `editorial-field / dom-led / 2 beats`；只有出现滚动、逐渐、穿越、进入或时间线等正向信号才使用 `continuous-scroll`。
- 视觉流程改为“机械门禁 → 独立视觉验收 → 失败时唯一一次证据驱动精修 → 复验”。原版本通过时不再先调用精修模型，常见成功路径减少一次模型调用。
- 全量 Vitest：60 个文件、217 项通过。`tsc --noEmit && vite build` 通过；仅保留项目既有的 Vite 扩展名和大 chunk 警告。
