# V2 用户意图来源隔离 R59

## 第一目标

用户只需要描述期望的想法。系统根据最终效果自行选择参考、素材、DOM、Canvas、Three.js 与生成方式，交付一个与目标相符、可运行、可理解的优秀网页。

## 本轮修正的问题

R54 验证文档把“无需外部素材”等实验便利条件写进了任务描述。它不是用户要求，却会被下游模型当成硬约束，导致可辨认主体退化成质量较差的程序化几何体。问题不在于模型能否生成素材，而在于系统没有区分约束来源。

## 新合同

- `rawUserBrief`：用户提交的原始想法，进入任务后不可被系统静默改写。
- `userConstraints`：仅提取用户明确表达的限制。
- `systemPreferences`：质量优先的实现建议，不能覆盖用户目标。
- `experimentConstraints`：仅用于测试和验收调度，不进入创意 brief。
- `assetPolicy`：固定为 `quality-first`；模型素材、项目素材、DOM、Canvas 与 Three.js 都是可选手段。
- `submissionSource`：记录工作台用户、API 客户端或系统验证，防止系统生成的测试 brief 被误认为用户输入。

旧任务没有来源记录时标记为“历史任务 / 来源未知”，不推断其中的实现限制已经获得用户确认。

## 工作台行为

工作台直接显示“用户原始目标”和“系统技术边界”。恢复历史任务时，文本框必须显示任务真正保存的 brief，不能继续显示 URL 中另一个过期想法。实验限制如果存在，单独展示，并明确它们不进入创意 brief。

## 停止边界与结论

本轮不调用模型、不生成新案例、不增加平台能力。只修复意图来源、工作台可见性和旧任务兼容；类型检查、相关测试与生产构建通过后即停止。

R59 让系统重新服从第一目标：用户决定“想要什么”，系统负责“用什么做到最好”，测试条件不能再伪装成用户限制。
