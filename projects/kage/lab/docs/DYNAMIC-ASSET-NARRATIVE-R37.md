# R37 · 动态素材叙事合同

## 目标

把 R36 温室案例中已经验证有效的做法接回主生成流程：用户只描述目标，模型按最终画面需要决定素材数量、素材职责和出现时机；素材生成器物化缺失素材；Codex 把素材、DOM 与 Three.js 编译为专属网页；机械评审和独立视觉验收共同决定最终版本。

这不是新的页面模板，也不要求固定三段或四章。

## 此前缺口

旧的 assetRequirements 只记录主体、环境、图片或模型等类别。素材生成器统一使用“16:9 hero”提示，Manifest 只接入第一张图片，Codex 只知道素材大致角色。因此系统可能已经生成了素材，却不知道它应该用于开场、变化过程还是最终画面。

## 当前合同

每个外部素材需求可以携带：

- anchor：0–1 体验时间线上最强视觉责任位置；
- function：建立、发展、转化、收束或持续；
- visualState：该时刻必须形成的画面；
- continuity：与前后状态保持何种主体、材质、光色或空间连续性；
- integration：透明主体、全幅环境、无缝场、空间对象或原生媒体。

素材数量由 brief 决定。无需真实素材时可以为零；一次完整变化可能需要多个关键素材；系统不把状态数等同于固定章节数。

## 执行链

    Creative brief
      -> model EffectSpec + dynamic asset experience contracts
      -> MiniMax image materialization / curated or user assets
      -> all generated assets attached to the selected manifest
      -> Codex dedicated bundle ordered by experience anchor
      -> required asset usage gate
      -> desktop opening / middle / ending / mobile review
      -> independent final visual acceptance
      -> one best result

## 强制门禁

- required=true 的素材必须在运行时代码中实际引用；
- 对应 bundle 声明也必须为 required=true；
- 只加载、隐藏、遮挡或放在不可见状态不构成视觉验收通过；
- 素材提示根据 integration 改变，不再把所有素材都生成成居中海报；
- 多素材按 anchor 进入 Codex 上下文；
- 提示词明确禁止固定三段、四章和等距时间点。

## 已验证

- 定向测试：4 files / 12 tests 通过；
- 完整测试：35 files / 104 tests 通过；
- TypeScript 与 Vite 生产构建通过；
- 温室精选素材会稳定返回开场种荚、纤维转化、成熟温室三个关键职责，而不是任意一张 hero。

## 下一验证

用一个此前没有专门案例的新 brief 运行完整链路，记录：

1. 模型是否提出合适且非固定数量的素材需求；
2. 素材生成耗时、缓存命中和总负载；
3. Codex 是否按 anchor 真实使用关键素材；
4. 初版与自动精修各自的视觉得分和缺陷；
5. 最终是否值得成为该目标唯一保留案例。

## 端到端实测

使用夜间生物材料温室 brief、Codex 5.6-terra 规划与代码生成、Codex 5.6-sol 视觉精修和独立验收执行了完整链路。

- 首次规划暴露严格 JSON Schema 不接受可选 experience 字段；已将模型输出 Schema 改为必填，同时保留本地旧规格兼容。
- 重试后规划、素材匹配、专属代码生成均通过；初版一次编译成功，编译耗时 836ms，实际引用三张 required 素材。
- 初版只有 20px 有效滚动距离，却仍把 progress 映射到 0–1；这证明只检查 progress 不足以判断滚动体感。
- 新增最小有效滚动行程门禁：桌面至少约 80vh，并禁止用全局 overflow:hidden 和仅 100vh 消灭纵向文档流。
- 后续三个候选机械评审均达到 100 分，滚动行程恢复到约 1,624–2,718px，横向溢出为 0。
- 独立视觉验收曾从 18–38 分提升到 84 分：三阶段职责和终局 CTA 已成立，但透明主体的矩形画布边界在桌面与移动端仍可辨认，因此仍未达到精选标准。
- 两次精修均被拒绝；任务被正确持久化为 failed，可从 reviewing 重试。没有归档新案例，R36 仍是该目标唯一最佳案例。

本次验证证明：动态素材合同和机械门禁已经进入真实主流程，但“代码引用素材”仍不等于“素材承担声明的视觉角色”。因此已追加角色级生成合同：透明主体不得被占位几何覆盖，全幅环境必须在对应 anchor 覆盖视口，resolve 素材必须在最终状态清晰可见并与 CTA 形成稳定构图。该增强将在下一次不同目标验证中复验。

## 工作流可靠性修复

端到端测试还暴露了一个与画面无关但会显著拖慢生成的问题：带 autorun 参数的工作台在 Vite 热更新或浏览器刷新后会重复创建 Codex 任务。现在启动策略已经改为“一次 autorun 对应一个持久化 job”：

- URL 尚无 job 时，autorun 才允许启动远程模型；
- job 写入 URL 后立即移除 autorun；
- planning / assets 阶段只恢复同一个 job；
- authoring / reviewing / refining / complete / failed 阶段由工作台恢复或展示，不创建替代任务。

该策略已有独立回归测试。所有本轮重复任务均已停止，未通过结果不进入案例库。

## 受控新目标验证：云端天文观测站

按照“一次规划、最多五个关键素材、一次初始构建、最多两轮精修、只保留一个通过结果”的停止条件，使用此前没有专门案例的云端天文观测站 brief 运行主链路。

- 第一次执行在素材阶段诚实阻断：模型声明了 environment，但路由没有识别其 full-bleed-environment 集成方式。现已只允许全幅或无缝场类型的虚构 environment 由图片适配器承担；真实 3D、HDRI、GLB 等需求仍保持阻断。
- 中国开放平台密钥与项目原国际站默认域名不匹配，接口返回 invalid api key。依据用户提供的官方手册，默认域名已改为 https://api.minimaxi.com/v1。
- 修正后 MiniMax image-01 真实生成一张 251,320 字节 JPG；素材、专属代码生成、TypeScript 编译和四状态浏览器采集全部完成。
- 初版及两次候选的机械评审均为 100 分，说明滚动行程、横向溢出、可达状态和运行错误门禁有效。
- 第一轮独立视觉验收 58 分：素材成为主画面，但同一外景图无法可信承担“接近—进入穹顶—星图展开”三种空间状态。
- 第二轮验收退化到 24 分：黑色蛋形占位几何遮挡素材，移动端拥挤，末段星图成为随机平面线网。
- 达到两轮停止条件后任务标记 failed，没有第三轮精修，也没有归档案例。

结论：MiniMax 本次输出足以承担电影化环境底图，不能单凭这一例认定它是主要质量瓶颈；更直接的问题是模型只规划了一张环境画面，却要求它承担多个不可由裁切完成的空间状态。下一次若继续验证，应在规划阶段拒绝“单素材承担多个不连续空间”的合同，而不是继续叠加精修轮次或新模型能力。
