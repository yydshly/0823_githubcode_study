# Kindergrimm Source-first Research Delivery Report

## Outcome

The research program now starts from the current upstream repository, proves its original capabilities with live upstream pages, separates reuse from genuine extension, and treats Scene Studio and the story demo as application proofs rather than source capabilities.

## Locked source

- Repository: https://github.com/albertobeiz/kindergrimm
- Commit: `5857b1e1cae2713d6714ad7dd7f89626bb242f0f`
- Observed scale: 135 JavaScript modules, 18 HTML entry points, 13 item families, 9 historical style backends.
- Runtime boundary: the inspected application does not call OpenAI, Anthropic, Gemini, or another hosted generation API at runtime. Its deterministic output is driven by JSON recipes, seeded random streams, procedural parts, render backends, rigs, and host applications.

## Corrected understanding

1. Kindergrimm is not merely a 2D picture generator. It is a deterministic procedural character and asset system spanning drawn 2D, Voxel 3D, Gloss 3D, procedural objects, animation, crowds, items, scenes, and games.
2. The latest source already owns nine style backends and a mature item system. Our Inkcut/Felt and Prop/Icon/Scene Component work remains useful engineering evidence, but is classified as `PARALLEL / REASSESS`, not a source-net-new capability.
3. NPC Factory review gates, runtime SDK, deterministic packaging, CRC/version manifests, and release workflows remain genuine extensions.
4. Scene Studio and the story demo validate consumption and user-intent workflows; they do not prove that the source repository contains those product interfaces.

## Research chain

`SOURCE ORIGINAL → MECHANISM REUSE → OUR EXTENSION → APPLICATION PROOF`

- Source original: Recipe/RNG, parts, hands/styles, rigs, drawn/voxel/gloss/object renderers, items, crowds, games.
- Mechanism reuse: deterministic identity and source-compatible recipe interpretation.
- Genuine extension: batch authoring, provenance, quality gates, Runtime SDK, release candidates, ZIP/CRC/versioned packaging.
- Application proof: intent-driven scene assembly and story/game consumption.

## Valid next increments

1. Source-version compatibility and recipe migrations.
2. Cross-backend identity: one character recognized across Drawn, Voxel, and Gloss.
3. Formal export and release pipeline for source assets.
4. Source-wide visual regression across seed, backend, item, pose, and style matrices.
5. Optional LLM intent adapter that only translates natural language into validated contracts; deterministic generation remains authoritative.

## Handoff questions

1. Can every visible claim be traced to upstream source, our extension code, or a labeled application proof?
2. Does a proposed feature add a capability the current upstream does not already own?
3. Does the same recipe keep identity across render backends and host applications?
4. Can the output be exported, versioned, reproduced, and regression-tested?
5. If an LLM is added, can the system still reject invalid intent and reproduce the same validated recipe without the model?
